# X 信息源扩容设计

**日期：** 2026-08-05
**状态：** 待用户审阅
**目标：** 提高 AI 日报中 X 信息源的覆盖度，同时维持现有事实、翻译和发布质量门禁。

## 背景

当前 X Feed 每四小时由 GitHub Actions 采集 25 个公开账号，VPS 只读取静态快照。X 候选在采集和编辑选择阶段已经可用，但每期日报的 X 条目上限为 3 条。2026-08-05 的快照包含 121 条推文，最终有 3 条 X 候选进入前 10 个写作候选，证明采集链路可用。

本次扩容不降低发布门槛。X 内容仍需通过现有的翻译、证据、质量复核和整期发布就绪检查。

## 决策

采用受控扩容方案：

1. 将正式来源由 25 个扩展到约 35 个。
2. 将 `DAILY_X_MAX_ITEMS` 从 3 提升到 5。
3. 将 X Feed GitHub Actions 单次任务时限从 12 分钟提升到 20 分钟，采集频率保持每四小时一次。
4. 账号按官方机构、研究者、行业媒体三个层级维护；每个账号在写入正式配置前，必须通过现有公开网页探针验证。

不采用拆分多工作流并行采集。该方案会增加快照合并、失败处理和排查成本，超出当前 MVP。

## 来源结构

| 层级 | 当前 | 目标 | 作用 |
| --- | ---: | ---: | --- |
| `primary` | 14 | 20 | 官方发布、模型和产品更新、研究公告 |
| `research` | 7 | 10 | 研究方向、技术解释和开发者观点 |
| `media` | 4 | 5 | 行业分析和生态信号 |
| 合计 | 25 | 35 | 保持覆盖面与可验证性的平衡 |

候选方向包括 xAI、Meta AI、Google AI、Microsoft AI、Cohere、Perplexity、字节 Seed，以及经验证可公开读取的研究者和行业分析账号。具体 `handle` 不以人工记忆为准，必须由探针验证后再进入 `config/x_sources.json`。

## 数据流与边界

```text
config/x_sources.json (约 35 个来源)
  -> GitHub Actions X Feed (每 4 小时，最长 20 分钟)
  -> x-feed 分支的 x-feed.json
  -> VPS XFeedCollector (快照时效默认 6 小时)
  -> 现有去重、时效过滤、评分与来源均衡
  -> DAILY_X_MAX_ITEMS=5
  -> 现有摘要、编辑复核、质量门禁、HTML 与微信草稿
```

`x-feed.json`、`XFeedCollector`、Docker Compose、RSS 采集和微信发布接口均不改变。单一来源采集失败仍只记录在快照的 `failures` 字段，不中断其他来源或 RSS 日报。

## 选择规则

- 每期日报最多 5 条 X 内容，不超过默认日报 10 条的半数。
- `primary` 与 `research` 层级继续在编辑选择中优先于普通社区信号。
- 同一账号、同一事件和同一主题仍受现有去重与来源均衡限制。
- X 条目不因来自官方账号而跳过翻译、证据或质量审核。

## 实施范围

| 文件或环境 | 修改目的 |
| --- | --- |
| `config/x_sources.json` | 加入经探针验证的官方、研究者与媒体来源，维持现有 schema。 |
| `.github/workflows/x-feed.yml` | 将顺序采集工作流的总时限调整为 20 分钟。 |
| `.env.advanced.example` | 将推荐示例更新为 `DAILY_X_MAX_ITEMS=5`。 |
| VPS `.env` | 显式设置 `DAILY_X_MAX_ITEMS=5`，不提交该文件。 |
| X 相关测试 | 覆盖扩容配置仍可加载、五条上限仍被来源均衡逻辑遵守。 |

本次不实现逐条记录“为何被发布过滤跳过”。该诊断是后续独立改造：当前报告只能统计 `source_only`、未翻译和高风险候选的总数，无法可靠归因到某一条 X 内容。

## 验收标准

1. GitHub Actions 手动运行后成功生成 `x-feed-v1` 快照，快照来源数约为 35，且至少有一个公开推文。
2. 快照的 `failed_source_count` 和 `failures` 可见；个别账号失败不阻断快照发布。
3. VPS 在快照生成后六小时内能读取 X 候选。
4. 来源均衡逻辑允许每期最多 5 条 X 候选，绝不超过 5 条。
5. 全量测试通过，RSS、HTML 日报、Docker 和微信草稿链路不回归。
6. 实际日报仍仅在现有发布门禁通过时创建微信草稿。

## 发布顺序

1. 在隔离分支更新来源配置、工作流时限、示例配置和测试。
2. 完成全量测试并创建 PR；合并后由 GitHub Actions 手动触发一次 X Feed 验证。
3. 检查 `x-feed` 分支快照的来源数、成功数、失败数和推文数。
4. VPS 在 `.env` 中设置 `DAILY_X_MAX_ITEMS=5`，用 `docker compose up -d --force-recreate` 重新创建容器。
5. 等待下一期定时日报，或经确认后手动运行一次，检查 X 候选数量、最终日报和发布状态。

## 风险与缓解

| 风险 | 缓解方式 |
| --- | --- |
| 新账号公开页不可稳定读取 | 先探针验证；失败账号不写入正式来源。 |
| 顺序采集耗时上升 | 将工作流时限提高到 20 分钟；保留每来源独立失败降级。 |
| X 单一来源陈述缺少交叉证据 | 保留既有 `source_only`、质量复核和发布门禁。 |
| X 条目增加挤占其他来源 | 5 条硬上限、同账号上限和日报来源均衡继续生效。 |
