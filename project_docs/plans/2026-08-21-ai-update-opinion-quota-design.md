# AI 圈动态与署名观点扩展设计

## 状态

方案 B 已获用户确认，等待用户审阅本规格后进入实现计划。

## 背景

当前生产流水线按硬新闻日报设计，允许 `fact_event` 和 `attributed_opinion` 两类内容，总量上限为 15 条，署名观点最多 3 条。X 快照中的项目进展、Benchmark、功能可用性、排行榜和研究者观点因此经常被当作硬新闻校验，最终以 `non_news_content`、`title_claim_not_source_bound` 或其它生成/绑定错误被排除。

项目目标是分享 AI 圈最新新闻、动态和观点，同时保留可追溯的原始证据和微信草稿的稳定发布边界。

## 目标

- 将单期日报最大展示量从 15 条扩展到 20 条。
- 新增明确的 `ai_update` 内容类型，用于 AI 圈项目、模型、功能、实验、Benchmark、排行榜和研究进展。
- 署名观点最多 8 条，目标尽量达到 5 条。
- `ai_update` 最多 8 条，目标尽量达到 5 条。
- 事实新闻继续至少 3 条；为达到 20 条，事实新闻可自然扩展到 4-7 条。
- 所有内容继续绑定规范来源证据；不以放宽总量为理由降低事实、归因、去重和安全规则。
- 内容不足时允许短版，不使用低质量候选硬凑数量。

## 非目标

- 不把所有 X 内容自动视为新闻或动态。
- 不取消原始证据、来源 URL、逐字引用、作者归因和事件去重要求。
- 不改变 X 快照采集方式、认证账号、Cookie 或 GitHub Runner 运行边界。
- 不修改真实 `.env`、微信凭证、服务器私有配置或运行时 `docs/` 产物。
- 不把动态/观点的目标数量变成必须满足的硬阻断条件。

## 内容模型

### `fact_event`

正式新闻事实。标题需要明确主体、事件动作和对象/结果，展示声明必须在规范来源证据中机械核验。事实新闻用于满足每期至少 3 条的最低要求。

### `ai_update`

AI 圈动态。接受以下类型的可追溯内容：

- 模型、产品、功能或服务的可用性/版本/能力进展；
- Benchmark、实验、排行榜或性能结果；
- 开源项目、研究项目或工具的具体进展；
- 官方账号或可信研究/技术账号发布的项目演示和技术说明。

动态不强制标题出现“发布”“更新”“融资”等硬新闻动作，但必须具备：

- 明确主体（组织、项目、模型、产品或完整人物/团队）；
- 明确对象或具体进展，不能只有“值得关注”“最新动态”等空泛表述；
- 原始文本中可逐字绑定的数字、版本、榜单、实验结果、功能或项目细节；
- 规范来源 URL 和可审计的原始证据。

活动报名、招聘、课程、产品广告、纯图片展示、转发、无上下文短句和无法绑定的泛泛评论不属于 `ai_update`。

### `attributed_opinion`

署名观点。只允许 `config/x_sources.json` 中明确标记 `opinion_eligible=true` 的自然人原帖。必须保留作者归因，且满足原帖、上下文完整、非转发、非推广和有实质性观点的现有规则。同一作者每期最多 1 条。

## 配额与选择

配置建议：

```text
DAILY_TOP_N=20
DAILY_MIN_FACT_ITEMS=3
DAILY_MAX_OPINION_ITEMS=8
DAILY_TARGET_OPINION_ITEMS=5
DAILY_MAX_UPDATE_ITEMS=8
DAILY_TARGET_UPDATE_ITEMS=5
```

新增变量使用与现有 `BriefingConfig` 相同的整数解析、预检和错误处理。`DAILY_CANDIDATE_POOL_N` 默认至少调整到 60，确保 20 条成稿有足够候选和回填空间。

选择器采用分阶段、可回填策略：

1. 从唯一事件中优先选择并验证 `fact_event`，确保达到 `DAILY_MIN_FACT_ITEMS`；
2. 在剩余名额中优先尝试 `ai_update` 和 `attributed_opinion`，直到各自达到目标 5 条或候选耗尽；
3. 继续按编辑分数、来源强度、新鲜度、主题/来源分散度和验证结果补充，单类不超过 8 条，总量不超过 20 条；
4. 某类候选不足时，由其它已合格类别补位；被拒绝、隔离或重复的候选不得回填；
5. 达不到 3 条事实或总量低于现有最低发布门槛时，`DraftDecision` 仍为 `block`；达到最低门槛但少于 20 条时允许正常短版。

动态和观点的目标是选择顺序，不是 `DraftDecision` 的硬配额。最终数量由有效、唯一、可绑定的候选决定。

## 生成与验证

- Builder 的输出继续使用 `title`、零至两个 `brief` 展示目标和证据绑定，由 Python 生成完整 claim。
- `fact_event` 使用现有严格事件动作和来源绑定校验。
- `ai_update` 使用单独的动态发布性校验：要求主体、具体对象/细节、原始证据绑定，不强制硬新闻动作；仍拒绝无证据新增事实、普通英文残留、泛泛标题和摘要越界。
- `attributed_opinion` 使用现有作者归因、原帖、上下文、推广和观点实质性校验。
- 质量 LLM 继续只读增强；不可用、超时或无效时，确定性规则通过的条目走 `rules_only`，不转人工复核。
- X 首次构建失败后的重建继续单条调用，并携带失败原因和保护锚点；不同失败原因继续分别审计。

## 决策、渲染与审计

- `BriefItem`、`BuiltBrief`、`SourceEvidence` 和 `DraftDecision` 支持 `ai_update`，并保持 JSON 向后兼容：旧数据缺失时默认 `fact_event`。
- `DraftDecision` 继续是唯一的 `create|block` 决策；增加事实、动态、观点的计数与上限诊断，不新增旁路发布状态。
- 日报 HTML 和微信正文显示内容类型标签，但每条仍只保留规范原始来源链接。
- `docs/debug/<date>-briefing.json` 记录分类、目标/上限、每次生成和验证轨迹、最终原因码；不写入密钥或完整外部响应。
- 运行时生成物不提交 Git。

## 失败与降级

- 单条来源、LLM、媒体或微信 API 失败继续按现有来源级隔离和流水线降级处理。
- `ai_update` 校验失败不自动降级为 `fact_event`，避免把圈内动态误写成硬新闻；若同一候选满足署名观点规则，可由采集分类阶段明确转为 `attributed_opinion`，不能由 LLM 擅自升级。
- 动态/观点目标未达到不阻断，只记录缺口和原因；事实最低数量、唯一性、证据绑定和微信安全边界仍是硬门槛。
- 总量达到 20 后停止消费候选；候选耗尽时生成实际数量，低于最低发布门槛则阻断。

## 测试范围

- 配置：20 条上限、观点/动态目标与上限、候选池下限和非法配置。
- 模型/序列化：`ai_update` 的 `SourceEvidence`、`BuiltBrief`、`BriefItem`、`DraftDecision` 往返兼容。
- 发布性：动态通过主体/具体细节/证据绑定，拒绝泛标题、广告、无上下文和无证据新增事实。
- 选择器/流水线：事实最低保障、动态/观点目标优先、单类上限、回填和总量 20。
- 决策：4+8+8 可创建，事实不足或重复残留阻断，短版不因目标缺口阻断。
- 渲染/最新产物：类型标签、来源链接和旧 schema 兼容。
- 运行完整 `python -m pytest -q`、`git diff --check` 和 `git status --short`。

## 验收标准

1. 新配置可表达事实至少 3、动态目标 5/上限 8、观点目标 5/上限 8、总量上限 20。
2. 一期包含至少 3 条事实且动态/观点合计可补足到 20 条时，`DraftDecision.action == "create"`。
3. 动态可以在没有“发布/更新”动作的情况下通过，但所有显示声明仍绑定原始证据。
4. 广告、招聘、课程、转发、无上下文短句和无证据新增事实仍被拒绝并留下精确原因码。
5. 观点作者归因、每作者一条、事实最低数量、唯一性和微信草稿安全约束不回归。
6. 现有旧 `fact_event`/`attributed_opinion` 产物可以读取，新增字段不会破坏 Flask、HTML、微信正文和诊断消费者。
