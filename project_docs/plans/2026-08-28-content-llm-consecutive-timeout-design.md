# 内容 LLM 连续超时熔断设计

## 背景

当前 `BriefBuilder` 在任意一次内容 LLM 请求超时后立即打开本期熔断。2026-08-27 服务器安全干跑中，前 11 次内容调用成功，第 12 次有效调用超时，随后 90 次构建尝试不再请求 LLM，45 条候选统一降级为 `content_llm_unavailable`，最终日报因条数和事实数不足而 `block`。

单次超时可能只是供应商或网络的偶发抖动，不足以证明后续请求都会失败。立即熔断保护了供应商，但放大了偶发超时对整期日报的影响。

## 目标

- 内容 LLM 只有连续 3 次请求超时才打开本期熔断。
- 第 1、2 次连续超时只影响当前请求，后续候选继续调用 LLM。
- 任意一次成功响应都将连续超时计数清零。
- 明确不可恢复错误继续立即熔断，不等待 3 次。
- 保留现有单条请求、SDK 禁止隐式重试、单条最多一次重建和安全降级边界。

## 非目标

- 不增加单条请求自动重试。
- 不增加并发、批处理或新的环境变量。
- 不修改 `DAILY_LLM_TIMEOUT` 的单次超时值。
- 不修改质量 LLM 或语义去重 LLM 的熔断策略。
- 不放宽翻译、逐字 quote、规范 URL、事实发布性或 `DraftDecision` 门禁。

## 方案

`BriefBuilder` 增加本期实例级连续超时计数，阈值使用模块常量 `3`。

### 请求成功

只要供应商返回可解析的响应对象并完成 JSON 解码，连续超时计数清零。后续 schema 或条目级畸形仍沿用现有 `invalid_builder_response` / `builder_item_*` 处理，不视为传输超时。

### 第 1、2 次连续超时

- 当前请求记录 `content_llm_timeout`；
- 连续超时计数加一；
- 不打开 `_circuit_open`；
- 当前条目继续走已有确定性来源回退；
- 下一个候选仍发起真实内容 LLM 请求。

### 第 3 次连续超时

- 当前请求仍记录 `content_llm_timeout`；
- 连续超时计数达到 3；
- 打开 `_circuit_open`；
- 当前条目继续走已有确定性来源回退；
- 后续候选不再调用 LLM，统一记录 `content_llm_unavailable` 和 `content_llm_circuit_open_count`。

### 立即熔断错误

现有不可恢复错误保持不变：HTTP 401、402、403、404、429、5xx，以及余额不足、无效 API key、模型不存在、网关不可用等明确供应商故障，第一次出现就立即打开本期熔断。

## 状态转换

```text
初始 consecutive_timeouts=0

timeout -> 1，继续
timeout -> 2，继续
success -> 0，继续
timeout -> 1，继续
timeout -> 2，继续
timeout -> 3，熔断

任意状态 + 明确不可恢复错误 -> 立即熔断
```

连续而不是累计计数，可以容忍被成功请求隔开的偶发超时，同时仍能在供应商持续无响应时停止请求。最坏情况下会额外等待 3 个 `DAILY_LLM_TIMEOUT` 周期；当前服务器值为 90 秒，即最多约 270 秒后熔断。

## 诊断与兼容性

- `content_llm_timeout_count` 继续统计实际超时请求数。
- `content_llm_circuit_open_count` 继续统计熔断后被跳过的构建调用数。
- 不改变既有原因码和公开 schema。
- 连续超时计数仅为 `BriefBuilder` 实例内部状态，不进入公开产物，也不新增配置。

## 测试与验收

使用 `tests/test_brief_builder.py` 覆盖：

1. 连续 2 次超时后，第 3 个候选仍真实调用 LLM，且成功后计数清零。
2. 连续 3 次超时后打开熔断，第 4 个候选不再调用 LLM。
3. `timeout -> success -> timeout -> timeout` 不熔断，证明成功会清零。
4. 401、402、429 和 5xx 等现有不可恢复错误仍第一次立即熔断。
5. 超时、熔断和回退原因码保持现有含义。
