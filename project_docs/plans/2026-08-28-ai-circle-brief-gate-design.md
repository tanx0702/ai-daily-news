# AI 圈快讯分类型门禁改造设计

## 背景

项目定位是每日 AI 圈快讯，内容应同时覆盖事实新闻、模型与工具动态、圈内人物观点，而不是只收传统媒体意义上的硬新闻。

2026-08-28 服务器安全干跑暴露了当前门禁与该定位的偏差：

- 131 条时效和 AI 主题过滤后的候选中，来源发布性预检只通过 19 条；
- 候选池返回 60 条，聚类和隔离后有 57 条进入内容生成；
- 26 条触发一次重建，因此内容 LLM 共成功调用 83 次；
- 最终只接受 5 条，其中 `fact_event=4`、`ai_update=0`、`attributed_opinion=1`；
- 52 条最终拒绝中，36 条为 `non_news_content`。

现有实现只有 X 候选会尝试分类为 `ai_update`，其它来源通常保持默认 `fact_event`。同时，X 动态分类要求结果关系与数字、榜单、指标或特定版本同时出现，模型演示、具体能力观察、工作流和工具进展即使具有明确新信息，也容易回退成 `fact_event`，随后被硬新闻门禁拒绝。

## 目标

- 在内容 LLM 调用前，对所有来源统一确定 `fact_event`、`ai_update`、`attributed_opinion` 或拒绝结果。
- `fact_event` 继续执行严格事实新闻门禁。
- `ai_update` 接受有明确主体和具体新信息的模型演示、能力变化、实测观察、工作流、开源工具进展和实际使用发现，不再强制数字、榜单或正式发布动作。
- `attributed_opinion` 继续只接受自然人原帖、完整上下文和明确立场。
- 纯推广、空泛感想、无上下文转发和未经证实传闻继续拒绝。
- 预检明确拒绝的候选不再调用内容 LLM；生成后的内容仍必须经过同类型最终门禁。
- 保持日报 5-20 条、至少 3 条事实内容，动态和观点各目标 5 条、上限 8 条，X 目标 5 条、上限 8 条。

## 非目标

- 不引入未经证实的爆料、传闻或匿名消息。
- 不取消逐条 quote、规范 URL、主体绑定、保护锚点或跨语言核验。
- 不允许 LLM 决定或改变 `content_type`。
- 不强制每天凑满 20 条，也不允许为了配额绕过最终门禁。
- 不修改采集源、X 登录方式、LLM 供应商、微信发布出口或公开产物 schema。

## 方案选择

采用“分类前移并使用独立门禁”。不采用只调阈值的方案，因为非 X 候选仍会被默认归为事实新闻；不采用统一评分制，因为评分无法替代可审计的来源和证据边界。

## 分类边界

分类是确定性编辑判断，在内容 LLM 前完成并冻结。先执行来源完整性、推广、传闻和上下文等通用拒绝规则；通过后，明确正式事件动作优先归为事实事件，符合自然人观点资格且没有正式事件动作的内容归为署名观点，其余再判断是否属于 AI 圈动态。

### 署名观点

候选只有同时满足以下条件才分类为 `attributed_opinion`：

- 来源是登记为可发表观点的自然人 X 账号；
- 是原帖，不是转发，回复或引用所需上下文完整；
- 命中确定性 AI 主题；
- 含有可提取的明确立场，而不是单纯转述链接、活动宣传或产品广告。

同一作者每期最多一条。机构账号即使使用观点语气，也不能进入自然人观点通道。

### 事实事件

候选具备来源明确支持的正式事件动作时分类为 `fact_event`，包括正式发布、版本 release、融资、收购、监管决定、论文或研究成果发布等。分类只识别来源已经表达的动作，不能根据模型生成内容升级事件强度。

GitHub 继续只接受具有项目说明和 release notes 的正式 release；stars、commit、recent push 等活跃度不能成为事实发布证据。

### AI 圈动态

不属于署名观点或事实事件的候选，在满足以下条件时分类为 `ai_update`：

- 有明确的模型、项目、产品、工具、研究团队或具体 AI 工作流主体；
- 有当前时间窗口内的具体新信息；
- 新信息属于能力演示、实测观察、实验发现、工作流变化、工具功能进展、开源项目具体进展或实际使用发现之一；
- 来源正文中存在一段可独立绑定该主体和具体进展的原始证据。

数字、榜单、指标、版本号和性能方向仍是强证据，但从必需条件改为可选条件。只有“很强”“很震撼”“未来已来”等态度词，没有可描述的新能力或行为时不构成具体进展。

### 直接拒绝

以下候选在分类阶段直接拒绝，不调用内容 LLM：

- 无明确 AI 主体或无当前新信息；
- 纯营销、抽奖、课程推广、招聘、会议邀约或导流；
- 只有无上下文转发、链接标题或元数据；
- 未经证实的传闻、匿名爆料或来源无法核验；
- GitHub 只有活跃度数据，没有正式 release 证据或可作为动态发布的正文证据；
- 无法构造规范原始来源证据。

## 数据流

```text
采集与时效过滤
  -> 规范化原始证据
  -> 确定性分类型
  -> 同类型来源发布性预检
  -> 聚类与候选池排序
  -> 内容 LLM 逐条翻译/摘要
  -> 同类型最终显示门禁
  -> 语义去重
  -> 按软目标回填
  -> DraftDecision
```

分类器输出冻结的 `content_type` 和原因码。Builder 只能翻译和摘要，不能返回或覆盖类型。Validator 必须按规范来源中的类型分派，不接受类型篡改。

来源发布性预检与最终 Validator 继续复用同一分派入口。分类器对教程、推广、未证实传闻等明确拒绝或证据无效时确定性终止；其它来源预检失败只降低尝试顺序，仍可在高质量候选不足时进入内容生成。无论预检结果如何，最终门禁都要重新检查生成后的标题、摘要和每项绑定。

## 分类型最终门禁

### `fact_event`

保持现有严格规则：明确主体、事件动作和事件细节必须由同一条规范来源证据支持；“发布、收购、融资、推出”等动作不得夸大或跨句拼接。

### `ai_update`

最终标题必须保留明确主体，并使用与来源一致的动态谓词，例如“展示”“测试”“观察到”“支持”“更新”“尝试”。没有正式事件证据时不得改写为“发布”“推出”或确定性行业结论。

每个标题或摘要声明仍必须由自己的绑定 quote 支持。绑定 quote 必须同时包含主体和该声明使用的具体能力、行为、实验、工作流或工具进展。数字型声明继续核验指标维度和方向；非数字型动态只要求可机械匹配的命名对象、具体行为或能力锚点，不再伪造数字要求。

### `attributed_opinion`

标题必须保留作者归因，摘要只能压缩作者原意，不能改写成无主语客观事实或机构公告。自然人资格、原帖、上下文和作者上限保持现有规则。

## 配额与回填

- 总量：目标最多 20 条，最低 5 条；
- 事实：最低 3 条；
- 动态：目标 5 条，上限 8 条；
- 观点：目标 5 条，上限 8 条；
- X：目标 5 条，上限 8 条。

目标只决定候选尝试顺序。流水线先保障 3 条事实，再优先补齐动态和观点缺口，最后按来源强度和编辑分数填充剩余名额。任何类别候选不足时可以由其它合格类别补位，但不能突破类别硬上限或用不合格内容凑数。

## LLM 与降级

- 内容 LLM 继续逐条调用，每条最多一次重建；
- 分类器明确拒绝和无效证据不消耗内容 LLM 调用；普通预检失败项只在通过项之后作为候补；
- 内容 LLM 失败时，来源回退仍要满足该候选已冻结类型的最终门禁；
- 质量 LLM 和语义去重 LLM 继续作为可选增强；不可用时，确定性规则通过的条目使用 `rules_only`；
- 质量 LLM 不得把 `ai_update` 升级成事实事件，也不得修正、补写或改变规范来源事实；
- 所有现有超时、熔断、quote 恢复和翻译失败原因继续保留。

## 审计与诊断

`docs/debug/<date>-briefing.json` 为每个候选补充或明确记录：

- 分类前输入的原始 `content_type`；
- 最终冻结的 `content_type`；
- 分类原因码和命中的主体/进展锚点；
- 预检结果；
- 是否因确定性拒绝跳过内容 LLM；
- 每次生成、重建、验证和最终原因码。

候选级分类细节只进入私有审计。汇总诊断在现有 `diagnostics.collection` 或 `diagnostics.selection` 容器中增加各类型分类数、预检通过/失败数、分类明确拒绝数和跳过的内容 LLM 数，不增加 `latest.json` 顶层字段，也不改变草稿和公开文章内容契约。

## 失败处理

- 分类器无法确认类型时保守拒绝，不交给 LLM 猜测；
- 同一候选同时具有事实动作和观点语境时，正式来源事件优先归为事实，纯个人判断归为观点，不允许一条占两个名额；
- 聚类后若强来源与弱来源类型冲突，以规范强来源的证据为准，弱来源不能提升事件强度；
- 最终动态不足时记录目标缺口，但不进入 `DraftDecision.reasons`；只有总条数或事实最低数不足才阻断草稿。

## 测试与验收

### 分类测试

- 非 X 的 RSS、HN 或专业媒体候选可以被分类为 `ai_update`；
- 有主体和具体能力演示、但没有数字的候选可以进入 `ai_update`；
- 有实测观察或工作流变化、但没有正式发布动作的候选可以进入 `ai_update`；
- 纯推广、空泛吹捧、传闻和无上下文转发被分类阶段拒绝；
- 正式发布仍归为 `fact_event`，自然人明确立场仍归为 `attributed_opinion`。

### 门禁测试

- 非数字动态的主体和具体进展能由单条 quote 完整绑定时通过；
- 动态把“展示”改写成“正式发布”时拒绝；
- 数字动态继续校验指标、维度和方向；
- 事实和观点现有安全测试保持通过；
- LLM 不能覆盖分类结果。

### 流水线测试

- 分类明确拒绝和无效证据候选不调用内容 LLM；普通预检失败项仅降序候补；
- 合格动态和观点按目标优先回填，事实最低数仍被保障；
- 类别不足不会硬凑，也不会把目标缺口变成草稿阻断原因；
- 审计能解释每条候选为何分类、是否调用 LLM 和为何入选或拒绝。

实现完成后运行受影响测试和完整 `python -m pytest -q`、`git diff --check`、`git status --short`。部署后只使用 `SKIP_WECHAT_DRAFT=1` 在服务器安全干跑，检查候选分类分布、内容 LLM 调用数、最终事实/动态/观点/X 数量和原因码；不以验证为名创建真实微信草稿。

## 文档同步

实现阶段同步：

- `AGENTS.md`：分类型门禁、明确分类拒绝和普通预检降序边界；
- `project_docs/pipeline.md`：分类、预检、生成和最终验证顺序；
- `project_docs/sources.md`：所有来源统一分类为动态的规则，以及 X 分类变化；
- 必要时 `project_docs/backend.md`：冻结类型和审计字段边界。
