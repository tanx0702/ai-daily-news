# 内容 LLM 逐条请求设计

## 背景

生产内容生成当前默认每次向 LLM 发送最多 5 条候选。服务器安全干跑中，一次较慢的批量请求超时后打开本期内容 LLM 熔断，后续候选直接降级，最终只有少量请求成功。当前模型更适合短输入、短输出的逐条翻译与摘要。

## 目标

- 生产内容 Builder 每次请求只发送 1 条候选，确保请求 JSON 的 `events` 长度恒为 1。
- 初次生成和失败后的重建使用同一逐条边界；X 失败重建继续遵守已有单条约束。
- 保留现有两次生成预算、确定性证据绑定、质量门禁、审计原因码和 `DraftDecision` 契约。

## 非目标

- 不新增批大小环境变量或其它配置入口。
- 不引入并发内容请求，不修改 LLM timeout。
- 不取消本期熔断；429、5xx 或网关不可用仍立即打开熔断，后续候选走既有降级。
- 不修改质量 LLM、语义去重、采集器、微信草稿或 X 快照逻辑。

## 方案比较

1. **固定单条请求（采用）**：把 `BriefingConfig.builder_batch_size` 的代码默认值和生产环境解析值改为 `1`。复用现有 Builder 和流水线，无新增配置面，改动最小。
2. **环境变量控制批大小（不采用）**：允许线上在 1 和 5 之间切换，但会增加配置、校验、模板和运维文档，超出当前需求。
3. **并发逐条或取消熔断（不采用）**：可能缩短总耗时或隔离单次错误，但会放大限流与供应商故障压力，并违反当前失败降级约束。

## 数据流与错误处理

`src.main` 通过 `BriefingConfig.from_env()` 获得固定的 `builder_batch_size=1`。事实简报流水线每次只从候选队列取一条，`BriefBuilder.build_batch()` 再把这一条交给 `_build_chunk()`，因此内容 LLM 的请求和响应都只包含一个事件。单条超时不会再使同一请求中的另外四条一起失败；但若错误满足现有熔断条件，本期后续单条请求仍停止调用供应商。

## 验收

- 配置默认值测试断言 `builder_batch_size == 1`。
- Builder 测试使用 6 条事件，断言产生 6 次 LLM 调用，且每次请求的 `events` 长度都是 1。
- 运行相关测试、完整测试、`git diff --check` 和 `git status --short`。
- 合并到唯一发布基线 `master` 后推送，服务器拉取并重建容器，再使用 `SKIP_WECHAT_DRAFT=1` 执行一次安全干跑；不调用真实微信草稿 API。
