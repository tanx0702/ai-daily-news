# 候选池有效产出修复设计

## 背景

2026-08-19 生产任务共采集 1572 条记录，时间和 AI 相关性过滤后剩余 94 条，但热度排序先截取 45 条，后续事实门禁又将其中 29 条判定为 `non_news_content`，最终只形成 4 条事实简报。当前流程在 `collect_candidates()` 排序时关闭发布风险降权，而真正的来源发布性校验到事实简报构建后才执行，因此池外候选无法回填。

## 目标

- 不降低事实、证据绑定、去重和最少 5 条门禁。
- 在候选池截断前复用确定性来源发布性规则，把可发布事件排在非新闻内容之前。
- 记录预检通过、拒绝和原因分布，便于区分采集不足与候选质量不足。
- GitHub 只提供有完整 release 证据的候选，并让标题明确表达 release 动作。
- Hugging Face 的 `lastModified` 不再被当作模型发布证据；没有明确发布证据时保留为采集诊断，不占正式候选池。
- arXiv 单次外部故障有有界重试；仍失败时记录并降级，不阻断其它来源。
- 服务器新闻窗口恢复为文档默认的 36 小时。

## 方案

### 候选预检与回填

采集器完成时间、AI 相关性过滤和证据保存后，对每个候选调用现有 `source_evidence_from_candidate()` 和 `validate_source_publishability()`。该步骤只执行确定性规则，不调用内容或质量 LLM。

候选分为 `publishable`、`rejected` 和 `invalid_evidence` 三组。评分排序分别在组内完成，返回池优先从 `publishable` 组取满 `DAILY_CANDIDATE_POOL_N`；只有发布性候选不足时才附加拒绝组，使后续审计仍能完整解释候选耗尽。诊断增加预检总数、通过数、拒绝数、无效证据数和原因计数。

### 来源修复

- GitHub release 标题由“仓库名 + tag”改为“仓库名 releases tag”，与 release URL、release notes 和发布时间共同构成可机械核验事件。
- Hugging Face API 的累计下载、点赞和 `lastModified` 只是活跃度信号。没有模型卡明确发布动作和说明时，候选标记为社区雷达并在预检阶段排除，避免把普通更新写成发布新闻。
- arXiv 对超时、429 和 5xx 最多重试一次，使用短暂退避；两次均失败则返回空列表并记录精确原因。

## 数据流

```text
所有来源 -> 时间/AI过滤 -> 保存规范证据 -> 确定性发布性预检
                                        -> 通过组按分数排序
                                        -> 拒绝组按分数排序并记录原因
                                        -> 优先通过组填充45条，必要时拒绝组补尾
                                        -> 聚类/构建/事实核验/语义去重/回填
```

## 验证

- 单元测试覆盖发布性候选优先、拒绝原因诊断、池容量回填和无效证据。
- GitHub 测试验证 release 标题具有动作且通过来源发布性规则。
- HF 测试验证只有活跃度元数据的模型不会占正式候选池。
- arXiv 测试验证瞬时失败重试成功以及连续失败安全降级。
- 完整执行 `python -m pytest -q`、`git diff --check`、`git status --short`。
- 部署后以 `SKIP_WECHAT_DRAFT=1` 执行生产入口，检查至少 5 条、来源分布、预检诊断和微信未被调用；之后恢复容器的原始生产配置。
